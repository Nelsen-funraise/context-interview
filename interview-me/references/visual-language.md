# 視覺化：訪談中與收尾

視覺化不是收尾才做的事。**訪談進行中就要給他看見自己的地圖在長**——那是這場對話最有說服力的一刻，而且它會讓他更願意繼續講。

---

## 訪談中出現四次，不是最後才出現

| 時機 | 給什麼 | 為什麼是這個時候 |
|---|---|---|
| **第 60 秒**（自查一結束） | **脈絡訊號圖 v0** | 他到這一刻只回答了一題，還在評估這件事值不值得投入。**先給再要**——哪怕圖上有兩個框是問號。他自己也說不出「我有 89 個 skill、9 個排程」這種數字，看到的當下他會意識到你真的做了功課 |
| 第一段問完 | **脈絡訊號圖 v1**（同一張更新） | 補上只有他知道的那幾塊。他會看到地圖從「你查到的」變成「我們一起補完的」 |
| 第二段選題前 | **工作矩陣** | 四個候選攤在同一張圖上比較，選題會快很多，而且他選的理由通常就藏在圖裡 |
| 第二段挖完判斷 | **閉環缺口圖** | 他剛講完的判斷還住在他腦裡。這張圖讓他看見從痕跡到每天在跑哪幾格是斷的——斷的那幾格就是藍圖要蓋的，收尾的藍圖才不會像憑空冒出來 |

同一張圖更新兩次，比最後給一張完整的更有效——**他看到的是自己的東西在成形，不是你交作業。**

節奏上不要每一輪都產圖。這四次就好，多了會拖慢訪談。

---

## 交圖的方式：講回去給他聽（雙向費曼）

圖交出去的那一句話，比圖本身更決定這場訪談的品質。

**不要問「這樣對嗎」「有沒有要補充的」。** 他還沒讀懂那張圖，沒辦法評價它——他會回「看起來不錯」，然後你就失去了這一次修正的機會。

**做法：先用他的日常把圖翻譯一遍，然後問一個具體的是非題。**

> ❌「這是你的脈絡訊號圖，有沒有要修改的地方？」
>
> ✅「我看到的是：你的東西主要放三個地方——行事曆、那份共用報表、還有你自己的筆記。其中筆記只有你看得到。所以每次有人問你『上次那個決定為什麼那樣做』，你得自己回去翻。對嗎？」

差別在哪：第二種給了他一個**具體到可以反駁的說法**。人很難補充一張圖，但很容易糾正一句說錯的話。

### 為什麼叫雙向

**你 → 他**：你把圖翻成他的語言，證明你真的看懂了他的工作。這是他決定要不要認真回答你的那一刻。
**他 → 你**：他糾正你的時候，用的是**他自己的話**。那句話是這場訪談最貴的資料——一字不改收進記錄頁的 `verbatim`，不要翻譯成正式用語（見 `references/interview-record.md`）。

### 三條規則

1. **一張圖只問一個是非題。** 問兩個他會挑好回答的答，另一個就靜靜地錯下去。
2. **翻譯要落到後果，不要停在描述。** 「你的筆記只有你看得到」是描述；「所以有人問你就得回去翻」是後果。人對後果才有反應。
3. **他說「對」也要再推一次。** 「那有沒有哪一塊我畫得太滿了？」——第一次點頭常常是禮貌。第二次才是真的。

### 你自己的檢查

翻譯不出來就代表你還沒懂。**如果你只能照著圖上的字唸一遍，那張圖就還不能交**——回去想到能用一句茶水間的話講出來為止（`references/plain-talk.md` 的費曼檢查）。

## 什麼內容配什麼視覺

不要全部做成單色長條圖。長條適合量級比較，但訪談的產出多半不是量級問題。

### 脈絡訊號圖：用訊號衰減編碼（範例見 `examples/context-map.html`）

把四個區塊排成一條**由左往右衰減的訊號帶**：

```
已經連上（實心）→ 可連未連（描邊）→ 只有你有（虛線）→ 沒被記錄（點狀）
```

- **最上面是訊號帶本體**：一排垂直短棒，密度與高度由左往右遞減，四區各用一種筆觸（實心 → 描邊 → 虛線 → 點狀）。最右端立一條實線，標「**▲ 自動化的天花板在這裡**」
- **訊號帶下方四欄對齊四區**，每欄列出該區的項目卡，卡片沿用同一套筆觸（實心底、實線框、虛線框、點狀框）——**填滿度＝訊號狀態，不是重要性**，這句要寫進來源行
- 標題上方放一排**大數字 stat**（他的專案數、skill 數、排程數⋯⋯自查得來的、他自己未必說得出的那幾個）。這排數字是「你真的做了功課」的第一眼證據
- 有他明顯的投入熱點（如 30 天提交數）就補一組單色橫條；有固定節奏（如每天同一時間的會）就補一條週間帶
- **訪談中萃取掉的缺口，當場改狀態**：原本在「沒被記錄」的那項若這場訪談已把它寫下來，就地換成實心卡＋「本次已萃取」小標——地圖自己展示訪談的效果，這是全圖最有說服力的一格

一眼要看得出「缺口在哪、訊號斷在哪」。看完只覺得「哇我有好多東西」是做失敗了。

**自查幾乎全落空時（新人、外部協作者、連接器沒開）**：v0 照樣要交，但換框架——四區都空就誠實畫空（描邊與虛線框保留、裡面標「查不到」），stat 排改放「查了哪幾個地方、各花幾秒」，標題那句改成「**我查不到你的痕跡——這本身就是第一個發現**」。空白地圖是合法產出；假裝查到了才是失敗。

### 工作矩陣 → 二維散布

橫軸**重複頻率**、縱軸**判斷含量**，四個候選放上去。

四個象限各有意義：右上（常做又需要判斷）是首選；右下（常做但機械）適合直接自動化不用訪談；左上（少做但判斷重）值得記錄但不急；左下不用碰。

**標出他選的那一個**，並在旁邊寫一句「每週約 X 小時」——選擇有了依據，之後回頭看也知道當初為什麼選它。

### 判斷規則 → 決策流程，不是清單

規則有分支和例外，用流程圖比條列清楚：主判準在中間，例外掛在旁邊，「要交給人」的出口單獨畫出來。

**例外要跟主規則一樣顯眼。** 沒有例外的規則到現場一定會誤判，而多數人畫圖時會把例外縮成小字。

### 案例軌跡 → 時間軸，用長度與深淺編碼

跨時間的狀態變化（哪幾次有進度、哪幾次只有討論、哪幾次消失）適合時間軸：每個時間點一根，用**高度或深淺**表示狀態強弱。

這裡適合單色階——因為狀態有順序（有進度 > 只有討論 > 沒出現），順序用深淺表達最直覺，用不同顏色反而會讓人以為是不同類別。

### 閉環缺口圖 → 迴路，出現兩次：先當診斷，再當計畫

固定六格一圈：

```
工作痕跡 → 記錄 → 萃取（判斷寫下來）→ 工具 → 每天在跑 → 新痕跡 ↩
```

**第一次（第二段結尾，診斷）**：把他這件工作對到六格上——已經存在的格子實心、斷掉或缺席的格子虛線＋醒目，標「你在這裡」。斷的格子旁邊寫一句證據（例：「LINE 裡的承諾沒進系統」＝記錄那格是斷的）。這張圖回答「為什麼要蓋東西」。

**第二次（建置藍圖裡，計畫）**：同一張圖，加上「下一格」箭頭，第一步就指著第一個斷掉的格子。這張圖回答「接下來蓋什麼、從哪格開始」。

**同一張圖出現兩次是刻意的**——他在藍圖裡認得這張圖，因為半小時前他親眼看它被畫出來、還修正過。這比收尾突然掏出一張新圖有效得多，也是他之後跟主管解釋這件事的道具。

## 共用的視覺原則

**單色為主，一個強調。** 底色系用灰階，只留一個強調色標「當前焦點」（他選的那個題目、他現在在的那一格）。不要用顏色編碼分類——顏色一多，讀者要先學圖例才看得懂圖。

**用位置、大小、填滿度傳達意義**，不要靠顏色。這樣灰階列印、深色模式、色盲都能讀。

**每張圖只回答一個問題。** 脈絡訊號圖回答「缺口在哪」，工作矩陣回答「該做哪個」，規則圖回答「怎麼判斷」。一張圖想同時回答三個問題，結果是三個都答不清楚。

**動效只給一個地方。** 唯一允許的動畫是閉環圖上「下一格」那條邊的行進虛線（marching ants）——它指著整份藍圖的重點。其他一律靜止，並包在 `@media (prefers-reduced-motion: no-preference)` 裡；列印時自然消失。兩個以上的動效會互相抵銷，等於沒有重點。

**文字仍是主體。** 圖是為了讓某一段話更快被理解，不是為了讓報告看起來豐富。沒有對應論點的圖就刪掉。

### Tokens

```
INK   #1C1C1A    PAPER #F0EFEB    CARD  #FBFAF7
MUTED #8F8E88    FAINT #C6C5BF    GRID  #DEDDD6
灰階  #1C1C1A #4A4944 #6A6963 #8F8E88 #B0AFA9 #C6C5BF #D8D7D1
深色  反轉，底 #141412、卡片 #1C1C1A
```

字體 Inter ＋ Noto Sans TC；數值 800 weight、`tabular-nums`。

公司有 design system 就讀它的 tokens 覆蓋顏色，但保留「不用顏色編碼資料」的原則（design system 的位置寫在 `references/organization-context.md`）。注意兩件常見的坑：簡報用的 design system 字級是為投影片設計的、用在報表要重新定；**品牌強調色多半不能當資料色**——飽和亮色對白底常常過不了 3:1 的對比門檻、先量再用。

## 產出形式

訪談中的三張圖與兩個成品（簡報骨架版在第①站、藍圖與定稿在交付段），優先發布成可分享的互動頁面（環境有 artifact 能力就用它，受訪者可以直接開、也可以轉給別人）。

環境不支援就寫成本機 HTML 檔再交付。**不要因為環境限制就退回純文字**——退回文字的那一刻，這一節的所有設計就都沒發生。

範例有兩份，都是真實訪談內容做的，直接照它們的結構與視覺標準做：

- `examples/context-map.html` — 脈絡訊號圖（訊號衰減圖＋stat 排＋投入熱點＋週間節奏＋天花板宣言）
- `examples/blueprint.html` — 建置藍圖（閉環圖含動效與底紋編號、規則卡、案例時間軸、一個第一步、討論題、前瞻驗收）


## 頁尾出處（授權要求，不是裝飾）

每一份渲染出來的成品，頁尾放一行小字：

```
由 {skill 名稱} skill 產出 · 方睿科技 FUNRAISE · CC BY-NC 4.0
```

使用者自己跑出來的成品照這樣標就好——那是出處，不是宣傳。

**但如果有人實質修改了這個 skill、又把改過的版本對外發布**，頁尾要改成：

```
Based on context-interview by 方睿科技 FUNRAISE；本版本已經修改，非方睿科技官方版本，亦未經方睿科技審查或背書。
```

理由與完整規則見 repo 根目錄 `NOTICE.md` 第四節：著作權授權不包含商標授權，改過的版本掛著原本的官方頁尾會讓人誤以為經過方睿審查。
