# 訪談記錄頁

**這場訪談只產出一個東西：一份會長大的頁面。**

不是「訪談時寫一份筆記、最後再另外做一份報告」——那是兩份東西、會不同步、而且第一份沒人看。這一份從第 60 秒就存在，每一站更新它，訪談結束時它就是交付物。

它同時要滿足兩種讀者：

- **人**：受訪者當場看得懂、看得到自己的東西被畫出來、可以直接轉給主管
- **下一個 AI**：三個月後他回來說「更新我的脈絡」，那個 agent 讀這一份就能接著談，不用重問

所以它是一頁 HTML：上面是給人看的圖與段落，最後嵌一段給機器讀的結構化資料。

---

## 它落在哪裡（三層，按環境選）

**先判斷你在哪一層，然後照那一層做。判錯的代價是他訪談完手上什麼都沒有。**

| 層 | 什麼時候 | 怎麼做 |
|---|---|---|
| **L1・有檔案系統** | 你能寫檔（Claude Code、有 Files 工具） | 寫成 `.html` 檔，第一次建檔時把路徑告訴他一次 |
| **L2・只有 artifact／畫布** | claude.ai 網頁、cowork、多數一般使用者 | 產成一個 artifact，**每站更新同一個**，不要每站開新的 |
| **L3・純聊天，兩者都沒有** | 只能來回文字 | 每站把「現在的結論」整段重貼一次；收尾把完整 HTML 原始碼貼給他，並說「複製存成 .html 就能打開」 |

**L2 是最常見的一層，也是最容易做錯的一層。** 錯法是每站產一個新 artifact，他最後有五份不知道哪份最新。規則很簡單：**一場訪談＝一個 artifact，從頭改到尾。**

三層都一樣：建立的那一刻講一句就好，之後每次更新都是靜音的。

> 「我開了一份記錄頁，我們講的東西都會寫進去，你隨時可以看。」

不解釋格式、不問他要不要、之後不再提。每更新一次就報告一次，他的回合會被這些話吃光。

---

## 什麼時候更新

**第 60 秒**：建立 v0。這時候只有抬頭和脈絡訊號圖草稿，其他區塊寫「進行中」。**先有東西，再有內容**——他看到一份已經開始長的東西，比看到一句「我等一下會給你報告」有用得多。

**之後每答完一題**：收到他的回答 → 先更新記錄頁 → 再想下一題 → 送出。順序不能換。

不要攢三題再一起寫。攢著的那一批，正好就是斷線時會不見的那一批；而且隔了三題再回頭補，你寫下的已經是你的摘要，不是他的話。

---

## 頁面上有什麼（七個區塊，順序固定）

1. **抬頭** — 誰、日期、談了多久、目前進行到第幾站
2. **你的東西都在哪** — 脈絡訊號圖。三類要分開畫：**已經連上的**、**可以連但還沒連的**、**只在你腦子裡的**。第三類是這張圖最有價值的部分
3. **今天的簡報** — 骨架版四區塊（今天最重要的一件事／行程／需要注意的／資料透明度）
4. **這件事** — 選中的那件工作：一週吃掉多少時間、他怎麼判斷、規則、例外
5. **下一步** — 第一個動作是什麼、誰要動、什麼時候
6. **還沒答的** — 待補清單，每條都要有「誰能答」
7. **給下一個 AI 的**（頁面最底、可摺疊）— 結構化資料，見下

前六區給人看，用他的話寫。第七區給機器讀，用固定 schema。

---

## 第七區：給下一個 AI 的

一段 `<script type="application/json" id="interview-record">`，內容照這個 schema。**欄位名不要自己改**——改了下一個 agent 就讀不到。

```json
{
  "schema": "interview-record/v1",
  "person": "受訪者名字或代稱",
  "date": "2026-08-29",
  "session": 1,
  "duration_min": 30,
  "status": "in-progress",
  "context": {
    "connected": ["行事曆", "共用報表"],
    "connectable": ["專案系統（有權限、還沒連）"],
    "only_in_head": ["每次決定要不要接案的判斷"]
  },
  "chosen_task": { "name": "", "hours_per_week": 0, "why_this_one": "" },
  "rules": [ { "if": "", "then": "", "quote": "他原話" } ],
  "exceptions": [ { "when": "", "do": "", "quote": "" } ],
  "open_questions": [ { "q": "", "who_can_answer": "" } ],
  "next_action": "",
  "verbatim": ["值得原樣留下的句子"]
}
```

`status` 只有兩個值：`in-progress`、`complete`。訪談中途斷掉就是 `in-progress`，下次接續談的 agent 看到這個值就知道要接下去而不是重跑。

`session` 是第幾次。第二次訪談時 `session: 2`，並在頁面抬頭寫「延續 ⟨上次日期⟩ 那一份」。

**`verbatim` 是這份檔案裡最貴的東西。** 三種一定要原樣留：他描述判斷的用詞（「感覺不對」「這種客戶我會先擱著」）、例外背後的理由、他自己用的比喻。這些詞本身就是判斷，翻成正式用語會走味。他講簡體就轉成繁體引用並標「（原文簡體）」。

---

## 後面推翻前面，就回頭改

記錄頁要回答的是「現在的真相是什麼」，不是「他今天依序講了哪些話」。

他在第 ③ 站說「其實不是三天、連續兩天我就會動手」的時候：**回頭把第 ② 站那段的三天改掉**，不要只在後面追加一條。改的那一行後面補「（他自己修正）」——「他改過主意」這件事要留，但頁面上只留一個版本的答案。

要回頭改的：結論、被推翻的數字與閾值、題目本身（中途換題很常見）。
不改的：`verbatim` 裡他的原話。那是證據。

**為什麼**：收尾要連續交出成品，那時候你沒有時間在流水帳裡判斷哪一句才算數。

---

## 待補清單：每一條都要有「誰能答」

他答不出來的東西不要追問第二次。當場記一條，往下走。

`廣告花多少要喊停 → 誰能答：Damon（他管預算表）`

「誰能答」只能填三種：一個具體的人名、一個系統或報表的名字、或「他自己回去查」。真的想不出來就填「不知道誰能答」——那本身就是訊號。**不准填「待確認」**，那等於沒寫。

---

## 不寫進去的東西

薪資數字、考核內容、對特定同事的評價，被動聽到也不寫。想加薪、想要設備這類訴求只記一句「有此訴求」，不記金額與細節。

---

## 頁面長相

沿用 `visual-language.md` 的視覺規格。額外三條：

- **未完成的區塊要長得像未完成**，不要留空白。寫「進行中」或「第 ③ 站會填」——空白會被當成「這裡沒東西」
- **一頁到底**，不要分頁、不要 tab。他要能一路捲下來看完，也要能整頁截圖傳給主管
- **不要放進度條與站點編號**——那是你的內部紀律。頁面上只出現他的東西
