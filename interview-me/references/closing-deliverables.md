# 交到他手上的兩個成品

訪談的價值在挖掘，但**受訪者記住的是最後五分鐘**。他不會記得你問得多準，他記得的是離開時手上有什麼。

所以他離場時手上一定要有兩個能打開、能給別人看、能照著做的東西——簡報骨架版第①站就先到手，藍圖與定稿在④⑤交付段。文字檔不算——那是留給系統的紀錄，不是給他的成品。

**交付時機：簡報骨架版在第①站、藍圖在第④站、簡報定稿與訂閱在第⑤站收尾（④⑤同一個交付段、一氣呵成）。** 骨架版的材料在第一站自查時就全部到手，當場排出來交給他——三輪實測證明放在收尾必被犧牲。收尾的簡報定稿交完接一句「要不要之後每天早上收到」，是整場訪談的自然終點——從「今天的成果」接到「明天開始的日常」。

**四條資料紀律（兩個成品都適用，實測踩過的坑）**：

1. 連結只用工具回傳的原樣 URL，且要直達那一筆（頁面連結，不是資料庫檢視）；只有資料庫連結就註明「開啟後找『XX』」。拼不出來就寫「來源：某某資料庫（未取得直達連結）」，絕不自己組連結
2. 查待辦與逾期任務，查詢條件必須含「負責人＝受訪者」——實測只用狀態＋日期過濾，同事負責的工作進了他的簡報，他的第一反應是「這不是我的」，信任當場扣分
3. 行事曆或資料源讀不到就寫讀不到，不要推論「你今天沒事」
4. 產出前最後一掃：有沒有簡體字、有沒有整段英文、每個數字有沒有來源行

## 成品一・他的第一份每日簡報

### 為什麼要真的產一份

訪談的第二份文件是「每日簡報設定」——那是一張設定表，對受訪者來說看不出價值。他要看到的是**那份簡報長什麼樣、裡面寫了什麼跟他有關的事**。

看過一次真的簡報，他才知道要不要每天收；沒看過，設定表就只是一份沒人會打開的附件。

### 怎麼產

**優先**：環境裡有每日簡報 skill（`daily-brief` 或同類）就呼叫它，把剛才的簡報設定當輸入。它有完整的模組庫與來源回溯規範，產出品質比你臨時寫的好。

**沒有的話不要跳過**，用下面的最小規格自己產。缺工具不是不交付的理由——受訪者不知道也不在乎你的環境裡裝了什麼。

### 最小規格（fallback）

用訪談中查到的資料，產一份**今天的**簡報，四個區塊：

1. **今天最重要的一件事** — 只有一件。用訪談時自查到的東西找（他的行事曆、逾期任務、最近的專案動態）。這一段要寫出「發生了什麼 → 它連動到什麼 → 建議動作」。真的找不到夠格的，就誠實寫「今天沒有需要立刻處理的事」，不要硬湊
2. **今天的行程** — 從行事曆來，標出他是不是主持人
3. **需要注意的** — 逾期任務或停滯項目，依天數排序，附連結
4. **透明度區塊** — 讀了什麼、沒讀什麼、這一版不會要你做任何事、怎麼停

每個數字都要能點回原始出處。**沒有連結的清單不要放**——他看到「這張還沒動」的下一個動作就是打開它。

輸出成 HTML，視覺照 `visual-language.md`。

**骨架版在第①站當場交**——不是替代品，是正式成品：材料在自查時已經全部拿到（行事曆、逾期任務、最近頁面），排版兩分鐘做得完。10 分模式收尾沿用這份**不重生**——他訂閱之後收到的第一份就是模組完整版，不承諾另外補送（「明早補」沒有人執行，是張空頭支票）；30 分模式收尾在骨架上加 1–2 個模組成完整版。**任何模式都不允許只交設定檔收場。**

## 成品二・建置藍圖（最終合成物）

### 這一頁的讀者不是他，是他要分享的對象

藍圖是整場訪談的合成：他拿著這一頁，30 秒內要讓主管或同事看懂「我在做什麼、為什麼值得、下一步是什麼」。所以開頭要有**三十秒讀完的脈絡回顧**（他是誰、地圖上找到什麼缺口、為什麼選這一題），中段是**第二段畫過的那張閉環缺口圖**（更新成計畫版：你在這裡、下一格是什麼），然後才是規則細節。

### 這不是知識卡

把萃取出的規則做成一張漂亮的「規則說明卡」是**錯的方向**。實測過：受訪者的原話是「這個規則視覺化對我來說沒有意義，我比較想要知道下一步怎麼把它變成真的在跑的東西」。

規則他本來就知道——那是從他腦袋裡挖出來的。他不知道的是：**這東西要怎麼接進我每天的工作**。

### 藍圖要回答的事

| 區塊 | 內容 | 為什麼要有 |
|---|---|---|
| 一句話 | 這個 skill 做什麼，用他自己訪談時的措辭 | 他要拿去跟別人講，得先有一句他唸得出口的話 |
| 脈絡回顧 | 三十秒讀完：他是誰、脈絡訊號圖找到什麼缺口、為什麼選這一題 | 分享對象沒有參加訪談，沒有這段他們看不懂下面在幹嘛 |
| 閉環缺口圖 | 第二段那張六格迴路的計畫版：實心＝已存在、虛線＝要蓋、標「你在這裡」與「下一格」 | 整頁的視覺主軸。他在訪談中看過並修正過這張圖，認得它 |
| 接在哪裡 | 什麼事件觸發它——接在他現有工作流的哪個點 | 這是「規則」變成「每天會自己跑的東西」的關鍵，也是他最想知道的一段 |
| 輸入 → 判斷 → 輸出 | 三欄流程圖 | 讓他一眼看出這東西吃什麼、吐什麼 |
| 判斷規則 | 主規則＋門檻，可展開看細節 | 給實作的人看 |
| 例外 | 什麼情況不適用、什麼情況要交給人 | 沒有例外的規則到現場一定會誤判 |
| 第一步 | **一個**動作：十分鐘內做得完、不需要新工具、**不增加他的日常工作量**。還沒接上組織資料入口的人、開通步驟就是最好的第一步 | 「有空再說」的最大成因是不知道從哪開始；「每通電話多記一欄」那種不是第一步，是加班 |
| 拿去討論 | 三個他可以拿去問主管或同事的問題。**紅線：不碰他的私有檔案或私有工具**，除非他自己先說想分享 | 他要能帶著這張圖去對話；但一題「要不要把你那張表交出來」會讓他下次什麼都不說 |
| 之後值得建的 | 工作清單裡排最前面的 1–2 項 | 讓他看到這不是一次性作業，是路線圖的第一步 |

最後附驗收三題怎麼跑、什麼時候跑（前瞻測試的排程在這裡寫清楚）。

### 互動要求

一頁 HTML，能在手機打開、能列印。互動只做**會改變他能做什麼**的那幾個：

- 判斷規則與例外可展開收合（第一眼看到骨架，要細節才展開）
- 第一步的動作項可勾選
- 內容全部在 DOM 裡，收合不等於不存在（列印時要完整、搜尋得到）

不要做假的儀表板、不要放動畫、不要把說明藏進導覽列。

## 視覺

兩個成品的視覺形式、tokens、以及「什麼內容配什麼圖」的選型，全部在 `visual-language.md`——**那是視覺規範的唯一出處**，這裡不重複，以免兩邊日後對不上。

一句話原則：單色為主、量級用長度不用顏色、每張圖只回答一個問題。

## 兩個常見失敗

**只交文字檔就結束。** 這是最常見的一種——文件寫得很完整，訪談者覺得交付完成了，受訪者覺得什麼都沒拿到。判準很簡單：**他離開的時候，手上有沒有一個能打開給別人看的東西？**

**成品做得漂亮但不是他要的。** 做視覺化之前先確認方向：他要的是「知道我的判斷長怎樣」，還是「知道接下來怎麼做」？多數情況是後者。不確定就直接問他一句，不要猜。

## 成本

這兩個成品是**一次性產出**，不是每天跑的排程，成本可控。但別為了華麗把單次成本推高——一頁乾淨的 HTML 勝過一個載入三秒的儀表板。
