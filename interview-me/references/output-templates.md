# 產出模板

SKILL.md 說的「留給系統的文件」四份，對應這裡的模板：脈絡訊號圖＝0、每日簡報設定＝0b、技能草稿＝1＋2＋3（工作流程與判斷條件是技能草稿的組成檔，一起交）、工作清單＝4。過目時給受訪者看的是全部。

檔名用受訪者名字開頭方便歸檔，例如 `jason-工作流程.md`。

---

## 1. 工作流程.md

給受訪者自己看的。目的是讓他覺得這場訪談對他本人有價值——這決定了他之後願不願意回來維護 skill。

```markdown
# ⟨姓名⟩・⟨決定名稱⟩ 工作流程

> 依 2026-XX-XX 訪談整理。有寫錯的地方直接改，這份是你的。

## 這個工作在做什麼
⟨兩三句話，用他自己的說法⟩

## 觸發時機
⟨什麼事情發生時要開始做這件事⟩

## 步驟
1. ⟨第一步⟩ — 需要的資訊：⟨從哪裡拿⟩
2. ⟨第二步⟩
3. …

## 停下來想一下的地方
⟨標出哪幾步不是照做，是要判斷的。這是這份文件跟一般 SOP 的差別⟩

## 做完之後怎麼知道做得好不好
⟨他自己驗證結果的方式與時間差⟩
```

## 2. 判斷條件.md

三份裡最難產出、也最有價值的一份。skill 能不能真的取代判斷，全看這份。

```markdown
# ⟨姓名⟩・⟨決定名稱⟩ 判斷條件

## 主要規則
| 條件 | 動作 | 來源案例 |
|---|---|---|
| ⟨A 且 B⟩ | ⟨動作⟩ | 案例 1、案例 3 |

條件要寫成可判定的形式。「數字太低」不行，「連續三天 ROAS < 1.5」可以。
還沒問到明確數字的，直接標 `⟨待補：閾值未確認⟩`，不要自己猜一個填進去——
猜出來的閾值會被後面的人當成事實。

## 例外
| 例外情況 | 改成怎麼做 | 為什麼 |
|---|---|---|
| ⟨情況⟩ | ⟨動作⟩ | ⟨受訪者的原話⟩ |

「為什麼」欄位盡量保留原話。他的用詞往往就是判斷的核心概念，
翻成正式用語會遺失資訊。

## 要交給人的情況
- ⟨情況⟩ → 找 ⟨誰⟩

這一段定義 skill 的邊界。沒有這一段的 skill 會在該停的地方繼續往前衝。

## 新人常犯的錯
- ⟨錯誤⟩ → 正確做法：⟨…⟩

這一段是從「新人最常犯什麼錯」那題來的，通常包含最難言傳的部分。

## 還沒問清楚的
- ⟨懸而未決的問題⟩

誠實留白。下次訪談從這裡接。
```

## 3. draft-skill/SKILL.md

驗收三題全中後，草稿交給計畫負責人（Nelsen）走 marketplace 送件；訪談者不自行提交，只負責把驗收紀錄與狀態標好。

進 marketplace 的草稿。

```markdown
---
name: ⟨kebab-case-名稱⟩
description: ⟨這個 skill 做什麼判斷、什麼時候該觸發。寫具體一點，
             包含使用者可能會用的實際說法⟩
---

# ⟨名稱⟩

> 來源：⟨姓名⟩（⟨職稱⟩）2026-XX-XX 訪談
> 驗收：⟨三題中幾題與當事人一致⟩
> 版本：v0.1，尚未經實際使用回饋迭代

## 這個 skill 判斷什麼
⟨一句話⟩

## 需要的輸入
- ⟨資訊⟩：⟨從哪裡拿⟩

拿不到的資訊要明講。skill 缺輸入時應該說「我需要 X 才能判斷」，
而不是硬猜——猜出來的答案看起來一樣有自信，這比不回答危險。

## 判斷規則
⟨從判斷條件.md 搬過來，改寫成給 agent 執行的指令⟩

## 例外
⟨同上⟩

## 遇到這些情況要停下來問人
- ⟨情況⟩

## 實際案例
⟨訪談裡的真實案例，三到五個，每個都寫：當時的資訊 → 做了什麼 → 為什麼 → 結果⟩

這一段是整份 skill 最不可替代的部分。規則可以被重寫，
真實案例不行——它們是這份 skill 唯一的事實依據，
也是後面的人判斷規則有沒有被改壞的參照點。

## 這個 skill 不做什麼
⟨明確劃界，避免被誤用在相鄰但不同的場景⟩
```

## 驗收紀錄

三題測完之後，把結果寫進 draft skill 的開頭。格式：

```
> 驗收：3 題中 2 題與當事人一致。
> 不一致的一題：⟨題目⟩ — skill 判斷 ⟨X⟩，當事人會 ⟨Y⟩，
> 原因是漏了 ⟨條件⟩。已補進判斷規則，未重測。
```

不一致的地方要寫清楚，不要只寫分數。後面接手的人需要知道這份 skill 的已知弱點在哪裡——一個標明弱點的 v0.1 比一個宣稱完美的 v1.0 有用得多。

## 0. 脈絡訊號圖.md（第一段的產出）

```markdown
# ⟨姓名⟩・脈絡訊號圖

## 已經連上的
| 資料源 | 裡面有什麼 | 誰能看到 |
|---|---|---|

## 可以連但還沒連的
| 資料源 | 為什麼值得連 |
|---|---|

## 只有你有的
⟨LINE 群組逐字稿、通話錄音、部門專用報表、個人電腦上的檔案⟩
註明目前存在哪裡、有沒有進到公司的系統。

## 完全沒被記錄下來的
⟨只留在他腦子裡的部分⟩

**這一段最重要。** 它是之後所有自動化的天花板——沒有被記錄下來的東西，任何 agent 都拿不到。
如果第二段挑的工作依賴這裡面的東西，要先解決記錄問題，否則 skill 做出來也跑不動。
```

## 0b. 每日簡報設定（④⑤交付段的定稿用這份挑模組；骨架版在第①站已交、不依賴本設定）

```markdown
# ⟨姓名⟩・每日簡報設定

## 角色
⟨一句話⟩

## 模組（第一份挑 1–2 個）

模組名以 `daily-brief` skill 的 `references/modules.md` 為準（同一個 repo，路徑是 `../../daily-brief/references/modules.md`）；下面這份是 2026-08-24 的快照，環境裡有該 skill 時以它的清單為準。

從下面挑。**第一份先給兩個以內**——人在看過之前不知道自己要什麼，看過三天他的回饋會非常具體，那時候再加。

**對外**
- 行銷漏斗：流量到名單的各段轉換
- 名單交接：新名單進來、誰該接、有沒有接
- 廣告健檢：投放異常、花費與成效落差
- 自然搜尋：關鍵字排名與內容成效
- 官網與內容上線：這週上了什麼、還有什麼卡著
- 市場訊號：公司登記異動、重訊、競品動態
- 客戶動態：往來客戶的最新狀況與待回覆
- 對外行程：拜訪、提案、活動

**對內**
- 業務管線：報價、成交、卡在哪一關
- 產品進度：開發中的東西走到哪
- 專案到期與狀態陳舊：快到期的、以及很久沒更新的
- 會議待辦落地：會議決議有沒有變成任務
- 跨部門協作卡點：等別人、別人等你的事
- 團隊 loading：誰手上太滿、誰空著
- 設計交付：設計需求與產出的排隊狀況

清單以外的也可以——**他講得出來的具體需求，比清單裡的選項更準。**
⟨依他的角色與脈絡訊號圖決定⟩

## 特別關注
- 專案：
- 對象／客戶：
- 指標：

## 不要出現
⟨訪談中他明確表示不想看的⟩

## 資料來源
⟨從脈絡訊號圖搬過來，只列他實際連上的⟩
```

## 4. 工作清單（這次沒做、但值得技能化的）

依「重複頻率 × 判斷含量」排序。判斷含量低的那些，通常適合做成單純的工具型技能，不需要再訪談一次。

| 工作 | 每週耗時 | 判斷含量 | 建議 |
|---|---|---|---|

這份是他之後的路線圖，也是下一次訪談的題庫。

---

## 存放位置與欄位

四份系統文件歸檔進公司 Notion：統一歸檔區由計畫負責人（Nelsen）指定；在他指定前，先存受訪者所屬團隊的工作區並告知計畫負責人。開場揭露「存進哪、誰看得到」時，講的就是這個位置與它的可見範圍。

每份歸檔頁面帶四個欄位：

| 欄位 | 值 |
|---|---|
| 受訪者 | 姓名（組織名冊拼法） |
| 產出者 | AI 訪談（迴音室規則：AI 產出不作其他 agent 的事實來源） |
| 狀態 | 未驗證 / 已驗收（附三題結果） / 已進 marketplace |
| 過目 | 受訪者過目日期——沒過目不歸檔 |

## 其他回饋（固定欄）

訪談中被動聽到的資源訴求（想加薪、想要設備）記在這裡，一句「有此訴求」即可，不記細節與金額，隨歸檔轉交計畫負責人。技能草稿與藍圖裡不出現這些內容。
